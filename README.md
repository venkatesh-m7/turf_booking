# Turf Booking API

A modular FastAPI backend for managing turfs, hourly slots, users, and bookings. The application uses PostgreSQL with SQLAlchemy, JWT bearer authentication, bcrypt password hashing, and Pydantic v2 validation.

## Features

- User registration and JWT login
- Public turf listing
- Admin-only turf creation
- Authenticated turf bookings
- Confirmed-slot double-booking prevention with a database constraint
- Operating hours and one clear hourly rate per turf
- Computed booking totals
- Booking owner cancellation
- Cancellation cutoff and waitlist promotion
- Customer ratings and reviews
- Admin booking oversight and analytics
- SQLAlchemy model relationships
- Request and SQL query logging to `app.log`
- Pytest coverage for authentication, turf, booking, waitlist, reviews, and analytics flows
- GitHub Actions CI on pushes and pull requests to `main`

## Requirements

- Windows 10 or later
- Python 3.10 or later
- PostgreSQL running locally or on a reachable server
- A PostgreSQL database named `turf_db` (or another database named in `DATABASE_URL`)

## Installation on Windows

Open PowerShell in the project directory:

```powershell
cd D:\turf_booking
py -3.10 -m venv venv
.\venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
pip install -r requirements.txt
```

If PowerShell blocks activation, run this once in an elevated or permitted PowerShell session, or use the interpreter directly:

```powershell
.\venv\Scripts\python.exe -m pip install -r requirements.txt
```

## PostgreSQL Setup

Create the database using `psql`, pgAdmin, or another PostgreSQL administration tool:

```sql
CREATE DATABASE turf_db;
```

The PostgreSQL user in `DATABASE_URL` must have permission to connect to the database and create tables.

## Environment Configuration

Create or update `.env` in the project root:

```env
DATABASE_URL=postgresql://postgres:your_password@localhost:5432/turf_db
SECRET_KEY=replace_with_a_long_random_secret
ALGORITHM=HS256
ACCESS_TOKEN_EXPIRE_MINUTES=60
```

Do not commit `.env`. It is already excluded by `.gitignore`.

### Special characters in the password

A password used inside a PostgreSQL URL must be URL-encoded. For example, an `@` character becomes `%40`:

```env
DATABASE_URL=postgresql://postgres:your%40password@localhost:5432/turf_db
```

Other commonly encoded characters include `%23` for `#`, `%2F` for `/`, and `%3A` for `:`.

## Run the Application

Start the development server with auto-reload:

```powershell
.\venv\Scripts\python.exe -m uvicorn app.main:app --reload
```

The API is available at:

- API root: http://127.0.0.1:8000/
- Swagger UI: http://127.0.0.1:8000/docs
- ReDoc: http://127.0.0.1:8000/redoc
- OpenAPI JSON: http://127.0.0.1:8000/openapi.json

Stop the server with `Ctrl+C`.

At startup, SQLAlchemy creates the tables defined in `app/models.py` if they do not already exist. For production deployments, use a migration tool such as Alembic instead of relying on automatic table creation.

## API Endpoints

All response examples are representative. IDs are generated by the database.

### Root

#### `GET /`

Health-style application response.

```json
{
  "message": "Turf Booking API is running"
}
```

### Authentication

#### `POST /auth/register`

Create a customer account. Passwords must contain at least 8 characters.

Request:

```json
{
  "email": "player@example.com",
  "password": "strongpassword"
}
```

Response: `201 Created`

```json
{
  "id": 1,
  "email": "player@example.com",
  "role": "customer"
}
```

Possible errors:

- `400`: email is already registered
- `422`: invalid email or password validation failure

#### `POST /auth/login`

Log in and receive a JWT. This endpoint uses OAuth2 form encoding, not JSON.

PowerShell example:

```powershell
curl.exe -X POST http://127.0.0.1:8000/auth/login `
  -H "Content-Type: application/x-www-form-urlencoded" `
  -d "username=player@example.com&password=strongpassword"
```

Response:

```json
{
  "access_token": "<jwt-token>",
  "token_type": "bearer"
}
```

Use the returned token on protected endpoints:

```text
Authorization: Bearer <jwt-token>
```

### Turfs

#### `GET /turfs`

Public endpoint that lists all turfs ordered by ID.

Response:

```json
[
  {
    "id": 1,
    "name": "Central Turf",
    "location": "Downtown",
    "hourly_rate": "150.00"
  }
]
```

#### `POST /turfs`

Create a turf. Requires a logged-in user whose database `role` is `admin`.

Request:

```json
{
  "name": "Central Turf",
  "location": "Downtown",
  "turf_type": "football",
  "open_time": "08:00",
  "close_time": "22:00",
  "hourly_rate": 150.00
}
```

PowerShell example:

```powershell
curl.exe -X POST http://127.0.0.1:8000/turfs `
  -H "Authorization: Bearer <jwt-token>" `
  -H "Content-Type: application/json" `
  -d '{"name":"Central Turf","location":"Downtown","hourly_rate":150.00}'
```

Responses:

- `201`: turf created
- `401`: missing or invalid token
- `403`: authenticated user is not an admin
- `422`: invalid request data

There is no public admin-promotion endpoint. To create an administrator, update the `role` column for a trusted user directly in PostgreSQL or add an administrative workflow before production use.

#### `PATCH /turfs/{turf_id}` and `DELETE /turfs/{turf_id}`

Admin-only endpoints for updating or deleting a turf. Deleting a turf also removes its related bookings,
waitlist entries, and reviews through the configured SQLAlchemy relationships.

#### `POST /turfs/{turf_id}/reviews`

Authenticated users who have booked the turf can submit one rating from 1 to 5 and an optional comment.

#### `GET /turfs/{turf_id}/reviews`

Public endpoint that lists reviews for a turf.

### Bookings

All booking endpoints require a bearer token.

#### `POST /bookings/`

Create a confirmed booking for an existing turf.

Request:

```json
{
  "turf_id": 1,
  "booking_date": "2026-09-15",
  "start_time": "18:00",
  "end_time": "19:00"
}
```

PowerShell example:

```powershell
curl.exe -X POST http://127.0.0.1:8000/bookings/ `
  -H "Authorization: Bearer <jwt-token>" `
  -H "Content-Type: application/json" `
  -d '{"turf_id":1,"booking_date":"2026-09-15","slot_time":"18:00-19:00"}'
```

The API validates the calendar date and time range, verifies that the slot is inside the turf operating hours,
computes `total_price` from the turf's single `hourly_rate`, and enforces confirmed-slot uniqueness at the
database level. Cancelled slots can be booked again.

Responses:

- `201`: booking created
- `400`: `Slot is already booked!`
- `401`: missing or invalid token
- `404`: turf does not exist
- `422`: invalid date or slot format

#### `GET /bookings/me`

Return the authenticated user's confirmed bookings, ordered by date and slot time.

Response:

```json
[
  {
    "id": 1,
    "user_id": 1,
    "turf_id": 1,
    "booking_date": "2026-09-15",
    "slot_time": "18:00-19:00",
    "start_time": "18:00",
    "end_time": "19:00",
    "total_price": "150.00",
    "status": "confirmed"
  }
]
```

#### `PATCH /bookings/{booking_id}/cancel`

Cancel a booking owned by the authenticated user.

```powershell
curl.exe -X PATCH http://127.0.0.1:8000/bookings/1/cancel `
  -H "Authorization: Bearer <jwt-token>"
```

Responses:

- `200`: booking status is changed to `cancelled`
- `400`: booking is already cancelled
- `401`: missing or invalid token
- `403`: booking belongs to another user
- `404`: booking does not exist

Cancellation is rejected inside the configured cutoff window (two hours by default). When a cancellation
opens a slot with a waiting customer, the oldest waiting entry is promoted to a confirmed booking.

#### `POST /bookings/waitlist`

Join the waitlist for a currently occupied slot. Use the same `turf_id`, `booking_date`, and time fields as
booking creation.

#### `GET /bookings/waitlist/me`

List the authenticated user's active waitlist entries.

### Administration

#### `GET /admin/analytics`

Admin-only summary of users, turfs, bookings, confirmed revenue, cancellations, and average rating.

#### `GET /admin/bookings`

Admin-only list of all bookings, including cancelled bookings and computed totals.

## Testing

Run the complete test suite:

```powershell
.\venv\Scripts\python.exe -m pytest -q
```

The tests use an isolated SQLite database and override the production `get_db` dependency, so PostgreSQL is not required to run the tests. The generated `test.db` file is ignored by Git.

Compile-check all Python files:

```powershell
.\venv\Scripts\python.exe -m compileall -q app tests
```

## Logging

The application writes request logs and SQLAlchemy engine SQL logs to:

```text
app.log
```

The log file is ignored by Git. Do not enable SQL logging in production if SQL statements could expose sensitive data.

## CI

The workflow at `.github/workflows/ci.yml` runs on pushes and pull requests targeting `main`. It:

1. Checks out the repository.
2. Sets up Python 3.10.
3. Installs `requirements.txt`.
4. Runs `pytest`.

## Production Notes

- Set a strong, randomly generated `SECRET_KEY` through the deployment environment.
- Never commit `.env` or database credentials.
- Use a managed PostgreSQL instance and TLS where appropriate.
- Use Alembic for schema migrations.
- Run behind a production ASGI process manager and reverse proxy.
- Add rate limiting, CORS policy, structured logging, and centralized error monitoring before exposing the API publicly.
- Add a formal admin-management workflow instead of changing roles manually.
- Confirmed booking slots use a database-level partial unique index, while the application pre-check provides the expected user-facing error for normal duplicate requests.
- Use a migration tool such as Alembic when applying schema or index changes to an existing production database.
